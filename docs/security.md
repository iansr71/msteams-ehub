# Security

How the E-Hub Teams Knowledge Assistant defends itself, how that is tested, and what is still open.

- **Threat model:** docs/threat-model.md covers the ten trust boundaries, the threats at each, and a residual risk register.
- **Controls and their tests:** `tests/security/controls.json`. It lists 21 controls, each with the tests that check it.
- **Latest results:** docs/security-test-report.md, generated by `pnpm test:security -- --write-docs`.

The results show what the code does with hostile input and hostile model output, tested without Azure, Moodle, Teams or a real model. They are not a penetration test, an audit, or a claim of compliance with any standard (including POPIA, ISO 27001 or SOC 2).

## Running the checks

| Command                              | What it does                                                                                                                                                                                                                  |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm test:security`                 | Runs every test listed in `controls.json`, then the secret scan. Prints pass or fail per control and writes `reports/security/security-test-report.{md,json}` (not committed). Exits 1 if any control fails or is incomplete. |
| `pnpm test:security -- --write-docs` | Also updates the committed docs/security-test-report.md                                                                                                                                                                       |
| `pnpm secrets:scan`                  | Scans every tracked file, and untracked files that are not ignored, for credentials. Reports file, line and rule, never the value.                                                                                            |
| `gitleaks detect --redact`           | Optional, if you have gitleaks. `.gitleaks.toml` configures the same allowances.                                                                                                                                              |

How a control's result is decided:

- **Pass:** every test listed for it ran and passed.
- **Incomplete:** a test was skipped. This counts as a failure, because a skipped check proves nothing. Two kinds of test skip when a tool is missing:
  - the Bicep checks (SEC-2) need the Bicep CLI (`az bicep install`, or `bicep` on the PATH);
  - the PowerShell deployment-script tests need `pwsh`.
    Install both before running `pnpm test:security` for a release.
- **Fail:** a test failed, or a listed test file or suite has no results. That catches renamed or deleted tests.

The secret scan reads the current files, not git history. A secret committed and then removed is still in history and must be rotated.

## Controls

### Prompt injection (PI-1, PI-2, PI-3)

- **Prompt structure.** System instructions, the question and the retrieved passages are separate parts of the prompt. Tags in user or document text that look like the prompt's own `<sources>` or `<question>` markers are defused.
- **Untrusted evidence.** Passages are labelled as untrusted evidence twice: in the system prompt and directly above the passages. The model is told to use them only as facts and never to follow instructions inside them.
- **No tools, no secrets.** The model has no tools; the system prompt says so and forbids revealing credentials, its rules or configuration. Nothing secret is ever in the prompt: retrieved text cannot ask for secrets the model does not hold, or for tools it does not have.
- **Grounding as the backstop.** The model's output must be JSON that passes schema validation. Every claim must cite a retrieved passage. Unsupported claims are removed, and if none remain the answer is withheld. So an injected instruction that makes the model invent facts, links or sources does not reach the user.
- **Hidden text is not indexed.** This covers:
  - comments, scripts and styles;
  - elements hidden by `hidden`, `aria-hidden` or role;
  - inline styles that hide text: `display:none`, `visibility:hidden`, zero size or opacity, off-screen positioning, clipping.
    Nothing a page links to or embeds is fetched.

### Input controls (IN-1, IN-2, IN-3)

| Control                     | Setting                                                          | Default          |
| --------------------------- | ---------------------------------------------------------------- | ---------------- |
| Question length             | `RAG_MAX_QUESTION_CHARS`                                         | see .env.example |
| Request body size           | fixed: 16 KB, checked on the declared length and while streaming |                  |
| Content type                | `application/json` only; strict schemas, unknown fields refused  |                  |
| Questions per user          | `API_RATE_LIMIT_QUESTIONS` per `API_RATE_LIMIT_WINDOW_SECONDS`   | 20 per 60 s      |
| Feedback per user           | `API_RATE_LIMIT_FEEDBACK` per window                             | 60 per 60 s      |
| Answers at once (all users) | `API_MAX_CONCURRENT_ANSWERS`                                     | 16               |

Questions are normalised to Unicode NFC, and control and bidirectional-override characters are removed from questions, source text and card text.

Rate limits are keyed by tenant and the validated Entra object ID, never by anything in the request body. They are checked before the body is parsed or Moodle is asked, so a refused request costs almost nothing. A refused request gets `429` with `Retry-After`. The limits are in memory, which suits the single API replica this deployment runs; a second replica would need a shared store.

### Output controls (OUT-1, OUT-2)

- **No markup is ever rendered.** The API returns JSON with `nosniff`. The bot renders answers as plain-text runs in Adaptive Cards, which do not interpret Markdown. It also defuses Adaptive Card date and time templates (`{{DATE(...)}}`). That covers HTML sanitisation, safe Markdown rendering and Adaptive Card escaping by construction: model output is never interpreted as markup, so there is nothing to sanitise into safety.
- **Only real, allowlisted links.**
  - Citations come only from retrieved chunks; invented or unknown sources are dropped.
  - Links must be `https` on an allowlisted Moodle host (`CITATION_ALLOWED_HOSTS`, default: the Moodle site).
  - The bot checks again (`TEAMS_ALLOWED_LINK_HOSTS`).

### Server controls (SRV-1 to SRV-4)

- **Headers.** The API and bot send these on every JSON response:
  - `Content-Type: application/json`, `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`;
  - `X-Frame-Options: DENY` and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`;
  - `Referrer-Policy: no-referrer` and `Cross-Origin-Resource-Policy: same-origin`;
  - `Strict-Transport-Security`.
    The admin page adds its own strict CSP.
- **CORS.** No `Access-Control-Allow-*` header is ever sent, and preflight requests are refused. The CORS allowlist is deliberately empty: the bot calls the API server-to-server, and the admin page is served from the API's own origin. If a browser client on another origin is ever added, add an explicit allowlist then.
- **CSRF.** The admin page uses bearer tokens from MSAL, never cookies, so a forged cross-site request carries no credentials. Every mutation must also send a same-origin `Origin` header, and destructive actions need `"confirm": true` in the body.
- **Timeouts.**
  - Every API request has `API_REQUEST_TIMEOUT_MS`.
  - Moodle calls and downloads have their own timeouts (`MOODLE_DOWNLOAD_TIMEOUT_MS`).
  - Readiness probes time out after 5 s.
  - The model provider has its own timeout and retry limit (`CHAT_REQUEST_TIMEOUT_MS`, `CHAT_MAX_RETRIES`).
- **Errors.** Error responses are a code, a fixed message and a reference ID only: no exception text, stack, URL or credential. The details go to the logs, redacted, under the same reference.

**TLS.**

- Azure Container Apps terminates TLS and refuses plain HTTP (`allowInsecure: false`). Clients get HSTS.
- In production, every `*_URL` and `*_ENDPOINT` setting must be `https`, and must not point at a loopback, link-local or metadata address; the services refuse to start otherwise.
- Moodle itself must serve HTTPS with a valid certificate (TLS 1.2 or later). The services verify certificates and have no option to skip that.
- For a local `docker compose` stack only, plain HTTP is allowed with `NODE_ENV=development`.

### Request forgery (SSRF-1, SSRF-2)

- **Fixed targets.** The indexer downloads only Moodle file URLs (`pluginfile.php`, `webservice/pluginfile.php`) on the configured Moodle host. A URL never comes from a user, a question or a document.
- **Redirects.** They are followed manually, only to approved hosts. Today that is just the Moodle host: the downloader accepts extra redirect hosts in code, but no setting configures any. The token is never sent on a redirect, and a redirect host that is a local address is refused.
- **Local addresses.** Loopback, link-local (including the cloud metadata service) and unspecified addresses are refused as service URLs and as redirect hosts, in any notation the URL parser accepts.
- **Paths and credentials.** Path traversal, other Moodle endpoints and credentials embedded in URLs are refused.
- **Not covered:** a host _name_ that resolves to a local address (DNS rebinding). The fixed host list limits this to a compromised Moodle or DNS.

### File processing (FILE-1, FILE-2)

- **Type and size.** The content type is decided from the file's bytes, not the declared type. Downloads are limited (`MOODLE_MAX_DOWNLOAD_BYTES`), as is extraction input (`EXTRACTION_MAX_INPUT_BYTES`).
- **Time.** Parsers run with a timeout (`EXTRACTION_TIMEOUT_MS`).
- **Archives** (docx, pptx):
  - limits on entry count (`EXTRACTION_MAX_ARCHIVE_ENTRIES`) and total uncompressed size (`EXTRACTION_MAX_UNCOMPRESSED_BYTES`), plus a per-entry limit and a compression-ratio check;
  - entry names checked for traversal.
- **Bad files.** Encrypted, unsupported and malformed files are recorded as failures with a category, and are never indexed partly.

### Authentication and authorisation (AUTH-1, AUTH-2, AUTH-3)

- **Entra tokens** are validated in full (docs/entra-sso.md): signature, issuer, audience, tenant restriction (`ENTRA_ALLOWED_TENANT_IDS`), expiry, version, scope and calling app. Identity comes only from the validated token, never from Teams message fields or the request body.
- **Course filtering happens before retrieval.**
  - It uses Moodle enrolments for the mapped Moodle user, as an integer-only search filter.
  - A course the user is not enrolled in is refused.
  - When Moodle cannot be asked, or the user cannot be mapped, the answer is refused (fail closed).
- **Administration** actions are checked on the server against the app roles in the token, for every endpoint and role.

### Secrets (SEC-1, SEC-2)

- **Start-up checks.** Configuration is validated at start-up. Problems are reported by variable name only, and production rules (https, no development switches) are enforced.
- **Redaction.**
  - Every secret setting is registered for redaction before anything else runs.
  - Logs and errors also redact `Bearer` and `Basic` values, JWTs, URL tokens and named credentials such as `api-key: …`, `client_secret=…` and `"password": "…"`.
- **Key Vault and managed identities.**
  - In Azure, the Moodle token, the bot secret and the Application Insights connection string are in Key Vault. Each service reads only the secrets it needs, through its own managed identity.
  - Azure AI Search keys are disabled, and Azure OpenAI is called with a managed identity.
  - Only local development uses keys from `.env`, which git ignores.
- **Secret scanning:** `pnpm secrets:scan`, with `.gitleaks.toml` as an option. The infrastructure tests also refuse committed tenant, subscription or client IDs.

## Operating securely

- **Rotation.**
  - The bot client secret has an expiry date: when it expires, sign-in stops for everyone. Rotate it before then. Update Key Vault and the bot's OAuth connection (`infrastructure/scripts/configure-bot-sso.*`), then restart the bot.
  - Rotate the Moodle token at least yearly, and immediately if it may have leaked. Generate a new token, update Key Vault, then restart the API and run the jobs. The full procedure comes with phase 20.
- **If a secret leaks** (in a log, a chat, a commit): rotate it first, then clean up. Removing it from a file or from git history does not make it safe again.
- **Least privilege in Moodle.** Give the service account a dedicated role with only the functions in docs/moodle-setup.md. Set a token expiry, and an IP restriction if the deployment uses the virtual network option.
- **Dependencies.** Run `pnpm audit` before each release. Automated dependency updates are not set up yet (docs/threat-model.md).

## Verified, and not verified

**Verified by automated tests** (docs/security-test-report.md):

- The 21 controls above, including the 12 attack scenarios Prompt 17 requires: user prompt injection, PDF prompt injection, hidden HTML instructions, forged course ID, forged identity fields, unauthorised resource URL, SSRF URL, oversized question, script output, malicious citation, token leakage through exceptions, and admin-role bypass.
- The attack tests run the real API: Entra token validation, Moodle authorisation, search, the answer engine and the citation checks. Only the model is scripted.

**Not verified:**

- **The real model.** Its behaviour is not tested, so prompt-injection resistance rests on the grounding and citation checks, not on the model obeying its instructions.
- **Teams and Azure.** That the Bot Framework, Teams clients and Azure behave as their documentation describes. This is first checked in the pilot.
- **Locking over Azure Files SMB** (docs/infrastructure.md).
- **Guests.** Whether guest accounts can complete Teams SSO.
